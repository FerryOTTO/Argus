# 多用户登录与会话管理

## 一、模块目标

### 1.1 问题定义

本模块需要解决的核心问题：OpenClaw 作为个人 AI Agent 框架，缺乏企业级的多用户身份认证与会话管理能力

| 问题 | 说明 |
|------|------|
| **单用户设计局限** | OpenClaw 定位为"个人 AI 助手"，所有操作以单一身份运行，无法区分不同用户的操作边界 |
| **缺乏身份认证体系** | 仅有简单的 Gateway Token 认证（`auth.enabled` + `auth.token`），无用户注册/登录/注销流程 |
| **无会话隔离机制** | 多通道（WhatsApp、Telegram、Web 等）共用同一个 Agent 身份和权限，无法按用户隔离 |
| **无法支撑 MAC 策略** | 会议确定的强制访问控制（MAC）需要基于用户角色做权限决策，但 OpenClaw 没有用户-角色体系 |
| **审计溯源困难** | 图结构日志需要关联到具体用户，但当前没有用户标识可用于归因 |

### 1.2 模块目标

为 OpenClaw 智能体框架提供**独立、可插拔的多用户认证与会话管理安全模块**，实现：

1. **多用户身份认证**：支持用户名/密码、OAuth2/OIDC、LDAP 等多种认证方式
2. **会话生命周期管理**：会话创建、维持、刷新、销毁的全流程管理
3. **用户-角色绑定**：支撑 RBAC（基于角色的访问控制），为策略引擎提供用户身份上下文
4. **会话安全**：防止会话劫持、伪造、重放等攻击
5. **可观测性**：所有认证和会话操作产生结构化日志，供审计层记录

## 二、业界主流做法

### 2.1 方案一：Session-Based Authentication（基于会话的认证）

**原理**：用户登录后，服务端生成唯一 Session ID 存储在服务端（Redis/DB），客户端通过 Cookie 携带 Session ID，服务端通过 Session ID 识别用户。

```
用户登录 → 服务端验证密码 → 生成 Session ID → 存储到 Redis
                                                ↓
客户端 ← 返回 Set-Cookie: sessionId=xxx ← ─────┘
  │
  │ 后续请求自动携带 Cookie
  ↓
服务端从 Redis 查找 Session → 识别用户身份
```

**优点**：

- **即时注销**：服务端删除 Session 记录即可强制登出
- **数据安全**：认证信息仅存储于服务端，降低泄露风险
- **实现简单**：适合中小规模应用，心智模型清晰

**缺点**：
- **扩展性受限**：需引入共享缓存（Redis Cluster），增加复杂度
- **跨域困难**：Session ID 绑定特定域名
- **粘性会话**：负载均衡需保持请求路由一致

**适用场景**：单体应用、中小规模系统、对实时注销有要求的场景

### 2.2 方案二：JWT Authentication（基于令牌的认证）

**原理**：用户登录后，服务端生成包含用户信息和权限的 JSON Token，用私钥签名后返回客户端。客户端每次请求携带 Token，服务端用公钥验证签名。

```
用户登录 → 服务端验证密码 → 生成 JWT（含 user_id, role, exp）→ 返回客户端
                                                                    ↓
客户端每次请求携带 Authorization: Bearer <JWT>
                                                                    ↓
服务端验证签名 → 解析 Claims → 识别用户身份
```

**JWT 结构示例**：
```json
{
  "header": { "alg": "RS256", "typ": "JWT" },
  "payload": {
    "sub": "user_123",
    "role": "analyst",
    "tenant": "military_dept_a",
    "iat": 1720800000,
    "exp": 1720803600
  },
  "signature": "..."
}
```

**优点**：
- **天然无状态**：任意服务节点可独立校验 Token，无需共享存储
- **高扩展性**：适合微服务、多终端架构
- **跨域友好**：Token 可嵌入 Header，不受 Cookie 域限制

**缺点**：
- **Token 不可即时撤销**：除非过期，无法强制登出（需引入黑名单机制）
- **Payload 可被读取**：敏感信息不应写入 Payload（虽不可篡改但可见）
- **密钥管理复杂**：密钥轮换需谨慎设计

**适用场景**：微服务架构、分布式系统、API 服务、多终端应用

### 2.3 方案三：OAuth 2.0 / OIDC（开放授权与身份认证）

**原理**：委托第三方身份提供商（IdP）进行认证，通过授权码流程获取 Access Token 和 ID Token。

```
用户 → 访问应用 → 重定向到 IdP（如 Keycloak）→ 用户登录 IdP
                                              ↓
IdP 返回授权码 → 应用用授权码换取 Token
                                              ↓
应用验证 ID Token（JWT）→ 获取用户身份信息
```

**优点**：
- **标准化协议**：业界广泛支持，生态成熟
- **单点登录（SSO）**：一次登录，多处访问
- **身份解耦**：应用不存储用户密码，降低安全风险
- **企业集成**：天然对接企业 IdP（Azure AD、Okta 等）

**缺点**：
- **架构复杂**：需部署授权服务器，流程交互多
- **依赖外部服务**：IdP 不可用会导致登录失败
- **实现成本高**：需理解 OAuth2/OIDC 协议细节

**适用场景**：企业级应用、SaaS 产品、需要 SSO 的场景

### 2.4 三种方案对比

| 维度 | Session-Based | JWT | OAuth 2.0/OIDC |
|------|---------------|-----|----------------|
| **数据存储** | 服务端（Redis/DB） | 客户端（Token） | 授权服务器 |
| **横向扩展** | 需共享缓存 | 天然支持 | 需授权服务器集群 |
| **即时注销** | 删除 Session 即可 | 需黑名单机制 | 令牌撤销端点 |
| **跨域支持** | 需额外配置 | 天然支持 | 天然支持 |
| **实现复杂度** | 低 | 中 | 高 |
| **企业 SSO** | 不支持 | 需额外实现 | 原生支持 |
| **适合场景** | 单体/中小系统 | 微服务/分布式 | 企业级/SaaS |

### 2.5 开源多用户认证系统参考

| 项目 | 功能特点 | 适用场景 |
|------|----------|----------|
| **Keycloak** | 功能全面的 IAM，支持 OAuth2/OIDC/SAML/LDAP，含 RBAC、SSO | 大型企业、复杂认证需求 |
| **Authelia** | 轻量级 SSO 门户，支持 OAuth2/TOTP/LDAP，反向代理集成 | 中小型项目、快速部署 |
| **SuperTokens** | 开源多租户认证，支持 RBAC、令牌轮换、盗用检测 | B2B SaaS、多租户平台 |
| **OAuth2-Proxy** | 简单 OAuth2 认证代理，对接 Google/GitHub 等 | 快速集成外部认证 |
| **SecureFlow** | Spring Boot 完整用户管理，BCrypt + RBAC + PostgreSQL | 参考实现、学习用途 |

### 3.2 当前认证机制分析

#### 3.2.1 认证方式（src/gateway/auth.ts）

OpenClaw 的 Gateway 支持以下认证方式：

```typescript
type GatewayAuthResult = {
  ok: boolean;
  method?: "none" | "token" | "password" | "tailscale" 
          | "device-token" | "bootstrap-token" | "trusted-proxy";
  user?: string;  // ← 仅为可选字符串，无结构化用户信息
  reason?: string;
  rateLimited?: boolean;
  retryAfterMs?: number;
};
```

| 认证方式 | 说明 | 多用户支持 |
|----------|------|------------|
| `token` | 共享密钥（`auth.token` 配置） | 所有客户端共用同一 Token |
| `password` | 单一密码保护 | 只有一个密码 |
| `tailscale` | 基于 Tailscale 网络身份 | 可识别不同 Tailscale 用户，但无角色管理 |
| `device-token` | 设备级别令牌 | 设备级而非用户级 |
| `bootstrap-token` | 首次启动令牌 | 一次性使用 |
| `trusted-proxy` | 信任代理转发 | 依赖外部认证 |

- `user?: string` 字段仅为可选字符串，**无结构化用户对象**
- 没有用户注册、登录、登出流程
- 没有密码哈希存储、用户数据库
- 没有角色、权限、组织等多用户概念

#### 3.2.2 会话管理分析

OpenClaw 的会话相关机制分布在以下模块：

| 文件 | 功能 | 分析 |
|------|------|------|
| `active-sessions-shutdown-tracker.ts` | 活动会话关闭跟踪 | 仅用于优雅关闭，非用户会话管理 |
| `approval-session-audience.ts` | 审批会话受众 | 用于操作审批流程 |
| `agent-runtime-identity-token.ts` | Agent 运行时身份令牌 | Agent 自身身份，非用户身份 |
| `boot.ts` | 启动与会话映射 | 系统启动时的会话初始化 |
| `auth-rate-limit.ts` | 认证速率限制 | 防止暴力破解 |
| `context-engine/` | 上下文引擎 | 2026-07-12 刚迁移到 SQLite 存储 |

- OpenClaw 的"会话"是消息通道会话（Channel Session），不是用户会话
- Lane Queue 机制确保每个通道的任务按序执行，但这是通道级而非用户级隔离
- 近期代码显示 session 存储已迁移到 SQLite（`flip sessions and transcripts to sqlite storage`）

## 五、方案

### 5.1 方案：JWT + Refresh Token + Redis 会话存储

综合考虑 OpenClaw 的架构特点（Gateway 中心化、WebSocket 长连接、多通道接入）和项目安全需求，推荐以下技术栈：

| 组件 | 技术选型 | 理由 |
|------|----------|------|
| **认证协议** | JWT (RS256) + Refresh Token | 无状态、Gateway 各节点可独立验证、适合 WebSocket 长连接 |
| **会话存储** | Redis | 支持 TTL 自动过期、高性能、适合会话实时销毁 |
| **密码存储** | bcrypt (cost=12) | 业界标准、抗彩虹表攻击 |
| **用户数据库** | SQLite（初期）→ PostgreSQL（生产） | OpenClaw 已使用 SQLite，初期保持一致 |
| **RBAC 实现** | 自研轻量级 RBAC | 项目需求明确且特殊（军工等级），自研更灵活 |
| **OAuth2/OIDC** | 可选扩展（Phase 2） | 初期优先用户名密码，Phase 2 对接企业 IdP |

### 5.2 选择理由

1. **无状态设计契合 OpenClaw 架构**：OpenClaw Gateway 是中心 Hub，JWT 无状态特性适合 Gateway 的分布式部署场景
2. **WebSocket 友好**：JWT 可嵌入 WebSocket 子协议头部，适合 OpenClaw 的 WebSocket 长连接
3. **即时撤销可通过 Redis 实现**：虽然 JWT 本身不可撤销，但结合 Redis 存储会话状态，可实现即时注销
4. **与审计层协同**：JWT Payload 可包含用户角色，供审计层记录和策略引擎决策
5. **渐进式扩展**：初期自研轻量实现，后续可无缝切换到 Keycloak/SuperTokens 等企业级方案

-- 用户表
CREATE TABLE users (
    id              TEXT PRIMARY KEY,           -- usr_xxx
    username        TEXT UNIQUE NOT NULL,
    display_name    TEXT NOT NULL,
    password_hash   TEXT,                       -- bcrypt，OAuth用户可为NULL
    security_level  TEXT NOT NULL DEFAULT 'internal', -- public/internal/secret/top_secret
    organization    TEXT,
    status          TEXT NOT NULL DEFAULT 'active',   -- active/suspended/disabled
    created_at      INTEGER NOT NULL,           -- Unix timestamp
    last_login_at   INTEGER,
    password_changed_at INTEGER NOT NULL,
    mfa_enabled     BOOLEAN DEFAULT FALSE,
    mfa_secret      TEXT                        -- 加密存储的TOTP密钥
);

-- 角色表
CREATE TABLE roles (
    id              TEXT PRIMARY KEY,           -- role_xxx
    name            TEXT NOT NULL,
    description     TEXT,
    min_security_level TEXT                     -- 最低安全等级要求
);

-- 权限表
CREATE TABLE permissions (
    id              TEXT PRIMARY KEY,
    role_id         TEXT NOT NULL REFERENCES roles(id),
    resource        TEXT NOT NULL,              -- agent/tool/knowledge_base/file/session
    action          TEXT NOT NULL,              -- read/write/execute/delete/admin
    resource_id     TEXT DEFAULT '*'            -- 特定资源或通配
);

-- 用户-角色关联表
CREATE TABLE user_roles (
    user_id         TEXT NOT NULL REFERENCES users(id),
    role_id         TEXT NOT NULL REFERENCES roles(id),
    assigned_at     INTEGER NOT NULL,
    assigned_by     TEXT,                       -- 分配者用户ID
    PRIMARY KEY (user_id, role_id)
);

-- 会话表（Redis 备份/持久化）
CREATE TABLE sessions (
    id              TEXT PRIMARY KEY,           -- sess_xxx
    user_id         TEXT NOT NULL REFERENCES users(id),
    roles           TEXT NOT NULL,              -- JSON数组 ["role_analyst", "role_admin"]
    security_level  TEXT NOT NULL,

);
