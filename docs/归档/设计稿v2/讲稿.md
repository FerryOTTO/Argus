# Argus 访问控制网关 — 讲稿

---

## 开场：一句话说清楚做了什么

我们做的是一个访问控制网关。打个比方：你公司里有四个级别的员工——实习生、普通员工、主管、老板。不同的文件、不同的工具，谁能碰谁不能碰，得有个东西管着。我们这个模块就是干这个的。

核心就是一个函数，四个参数扔进去——谁、想碰哪个目录、想调用什么工具、想查哪个数据库——返回一个结果：放行还是拦截。

---

## 第一部分：整体是怎么设计的

### 先看数据流

用户的请求过来，先经过网关验证 JWT，拿到用户身份。然后我们把用户等级注入到规则引擎里，再调 `check()` 做判断。通过了就放行，不通过直接拒绝。

### 规则怎么存

规则不在代码里。我们用了两个纯文本文件，竖线分割，改完就生效，不用重启。

- **users.txt**：谁是什么等级、有没有特殊权限
- **resources.txt**：什么资源需要几级才能碰

等级分了四级：public、internal、secret、top_secret。

### 判定逻辑

不是简单的比大小。有三层：

第一层，缺了资源目标直接拦。第二层，先看用户有没有特例——比如 admin 配了 `*`，那就全放行；反过来如果配了 `!`，那这个资源打死也不让碰。第三层才走等级比对——你的等级大于等于资源需要的等级，就放行。

还有一个关键设计：零信任。resources.txt 里没写到的资源，默认需要 99 级。也就是说，没被明确授权的，一律拒绝。

### 为什么这么设计

一个是规则和代码分离。改规则的人不用懂 Python，改代码的人不用担心业务规则被写死。

另一个是特例机制。等级做批量管理，特例做个别调整。比如给某个实习生开放一个特定目录，不用把他提到 internal，加一条特例就行。

## 第二部分：代码怎么实现的

### 核心函数就一个

`check()` 函数大概二十行，逻辑很直：检查参数 → 查等级 → 扫特例 → 比对等级 → 返回结果。

### 资源匹配

同一个函数处理三种匹配方式：路径用 glob 通配符、工具用前缀精确匹配、其他情况子串兜底。调用方不用关心匹配细节，扔进来就行。

### 和外部用户的对接

用户的等级不是写死在 users.txt 里的——是通过 `sync_external_user()` 动态注入的。JWT 里带了用户的 `security_level`，验证之后调这个函数塞进内存的规则表里。这样的话，用户表在那边的数据库里维护，我们的规则引擎保持同步。

### 砍掉了什么

刚开始想过做很多东西——Shell 注入检测、OPA 策略引擎、六层拦截管线。后来开会明确了需求方只要一个干净的核心。所以这些都砍了，就留一个函数加两个文件。

## 第三部分：怎么接入同学的模块

### 调用的时机

在 JWT 验证完之后、真正动手干活之前。就两行代码的事：

```python
sync_external_user(user_id, security_level)
if not check(user_id, path=..., tool=...):
    return {"error": "access denied"}
```

### 三种对接方式

**HTTP 代理**：请求发到 `/api/openclaw/xxx` 的时候，把 path 和 tool 提取出来，调 `check()`，通过了才转发到 OpenClaw。

**聊天 WebSocket**：用户发自然语言过来，用正则提取里面的路径和工具关键词，做预检。block 了就直接回提示，不用等 LLM。

**工具实际调用**：这是更理想的做法——不猜用户说什么，而是等 LLM 真正要调工具的时候，拦截 `tool_call` 事件，对真实的工具名和路径做检查。不过这个目前还在完善方案里。

## 第四部分：测试

### 账号体系

我们建了四个测试用户，对应四个等级：

- adminuser，top_secret，管理员
- robertwright，secret，主管
- benjaminsmith，internal，普通员工
- williamsims，public，外部访客

密码统一 test12345。

### 单元测试

`auth_gateway.py` 自带了 16 项单元测试，16/16 通过。覆盖了正常放行、等级不足、特例放行、特例拒绝、未知用户、空参数等各种场景。

### 聊天管道实测

我们用 williamsims（最低等级）登录，在聊天里发了三句话：

- "看看 C:\Windows 里面有什么"——直接拦截，因为 Windows 目录需要 4 级
- "帮我执行 dir 看 C 盘 Windows"——也被拦截，路径检查 + 工具检查都过不了
- "看看 D:\bilibili 里有什么视频"——放行，因为 bilibili 设了 public

### 完整的权限矩阵

我们跑了一遍所有用户对关键资源的访问，结果跟预期完全一致。C:\Windows 和 execute_bash 只有 adminuser 能碰；项目目录 E:\tiaozhanbei\MAC 和 write_file 到 robertwright 为止；Desktop 和 read_file 到 benjaminsmith；bilibili 和 query_weather 所有人能用。没在规则里的路径，比如 E:\epic，除了 adminuser（有 `*` 特例），其他人全部拦截。零信任生效了。

## 第五部分：后续要完善的点

现在有几个明显的问题：

**工具拦截的精度不够**。现在聊天管道是拿正则猜用户话里的关键词——"创建"匹配 write_file、"执行"匹配 execute_bash。用户换个说法就可能绕过。正确的做法是：不管用户说什么都先转发，等 LLM 真正要调 `tool_call` 的时候再去拦。

**路径和工具的交叉约束**。现在路径和工具是分开检查的。比如你可以设"Desktop 目录 internal 能进"，也可以设"write_file 要 secret"，但你没办法说"Desktop 目录可以读但不能写"。这两个是独立判断的。

**HTTP 代理管线还没挂 check**。`/api/openclaw/*` 的转发路径目前只做了用户认证，还没接 ACL。

**没有审计日志**。谁在什么时候访问了什么、被拦了还是放行了，完全没有记录。

这四个是我们下一步要做的。
