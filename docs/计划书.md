# Clawguard 访问控制系统改进计划书

## 一、项目概述

### 1.1 项目背景
当前 Clawguard 访问控制系统已实现基于角色的访问控制（RBAC），通过 `users.txt` 和 `resources.txt` 配置文件管理用户权限等级与资源访问规则。系统支持四级安全等级（public/internal/secret/top_secret），并通过 `check()` 函数完成权限判定。

### 1.2 改进目标
根据项目会议纪要，本次改进围绕三个核心方向展开：
1. **引入强制访问控制（MAC）机制**，构建 RBAC + MAC 双模型架构
2. **完善规则管理机制**，提供规则的增删改查接口
3. **细化权限控制粒度**，实现树状化资源权限管理

### 1.3 术语说明

| 术语 | 说明 |
|------|------|
| RBAC | Role-Based Access Control，基于角色的访问控制。用户权限由管理员分配的角色决定，角色可动态变更 |
| MAC | Mandatory Access Control，强制访问控制。用户和资源的安全标签由系统强制分配，不可随意更改，访问规则由系统强制执行 |
| 安全等级 | 当前 RBAC 中的四级权限（public/internal/secret/top_secret），本质为角色 |
| 安全标签 | MAC 机制中系统强制分配的不可更改的标记，用于决定访问权限 |
| 特例规则 | `users.txt` 中以 `!` 前缀表示显式禁止，`*` 表示允许所有的特殊规则 |

### 2.2 现有核心代码

**权限判定函数**（`v2/auth_gateway.py:211-247`）：

```python
def check(user_id, path="", tool="", database="") -> bool:
    # 1. 请求必须有资源目标
    if not any([path, tool, database]):
        return False
    
    # 2. 解析用户等级（从 users.txt 或外部注入）
    level = _store.get_user_level(user_id)
    if level is None:
        if BLOCK_UNKNOWN_USERS:
            return False
        level = DEFAULT_USER_LEVEL  # 默认 public=1
    
    # 3. 特例优先（!前缀=禁止, *=允许所有）
    specials = _store.get_user_specials(user_id)
    special = _check_special(specials, path, tool, database)
    if special == "block":
        return False
    if special == "allow":
        return True
    
    # 4. 等级比对：user_level >= required_level → 放行
    required = _resource_required_level(path, tool, database)
    return level >= required
```

### 2.3 现有问题

| 问题 | 说明 | 影响 |
|------|------|------|
| 纯 RBAC，无 MAC | 当前 `security_level` 本质是角色，管理员可随意修改，非系统强制标签 | 无法满足高安全场景下的强制访问控制需求 |
| 无规则增删改接口 | 只能通过直接编辑 `users.txt`/`resources.txt` 修改规则，无 API | 无法对接管理前端，运维效率低 |
| 权限粒度粗 | 基于 fnmatch 通配符匹配，无层级继承机制 | 规则膨胀，难以管理深层目录结构 |
| 聊天管道拦截不完整 | 仅做了第一层关键词猜测拦截（`browser_to_bridge`），第二层真实 tool_call 未拦截 | LLM 实际调用工具时可能绕过权限检查 |

## 三、改进方案

### 3.1 改进一：RBAC + MAC 双模型架构

#### 3.1.1 设计思路

保留现有 RBAC 能力，叠加 MAC 机制。两种模型独立运行，通过全局开关切换或组合使用。

```
┌─────────────────────────────────────────────────────────────┐
│                    访问控制模式选择                           │
│              ┌─────────┬─────────┬──────────┐              │
│              │  rbac   │   mac   │  hybrid   │              │
│              └────┬────┴────┬────┴─────┬────┘              │
│                   │         │          │                    │
│                   ▼         ▼          ▼                    │
│              ┌─────────┐ ┌─────────┐ ┌─────────────────┐   │
│              │ 角色比对 │ │ 标签比对 │ │  RBAC && MAC   │   │
│              │ users.txt│ │ 安全标签 │ │   双重校验      │   │
│              └─────────┘ └─────────┘ └─────────────────┘   │
└─────────────────────────────────────────────────────────────┘
```

#### 3.1.2 RBAC 与 MAC 核心区别

| 维度 | RBAC（现有） | MAC（新增） |
|------|-------------|------------|
| 权限来源 | 管理员在 `users.txt` 中配置 | 系统根据安全策略强制分配安全标签 |
| 可变性 | 管理员可随时修改用户等级 | **用户和管理员均不可更改**安全标签 |
| 资源标记 | `resources.txt` 中人工配置等级 | 资源创建时由系统强制打上安全标签 |
| 访问规则 | 用户等级 ≥ 资源等级 → 放行 | 下读上写（简单安全规则 + *-属性规则） |
| 绕过可能 | 管理员可绕过 | **任何人无法绕过**，包括管理员 |
| 适用场景 | 普通业务权限管理 | 高安全等级环境（军事、政府、金融核心系统） |

#### 3.1.3 MAC 安全标签设计

```python
# 安全标签结构（不可更改）
class SecurityLabel:
    """
    MAC 安全标签，由系统强制分配，不可修改
    
    格式: (等级, 类别集合)
    示例: (3, {"财务", "核心"})  # secret 等级 + 财务/核心类别
    """
    level: int           # 1-4, 对应 public/internal/secret/top_secret
    categories: set[str]  # 类别标签，用于更细粒度的 compartment 隔离
    
    def dominates(self, other: "SecurityLabel") -> bool:
        """简单安全规则：self 等级 ≥ other 等级，且类别包含"""
        return self.level >= other.level and self.categories >= other.categories
```

#### 3.1.4 MAC 访问规则

```python
# MAC 核心规则（系统强制执行，不可绕过）

def mac_check_read(user_label: SecurityLabel, resource_label: SecurityLabel) -> bool:
    """
    简单安全规则（下读）：
    用户等级 >= 资源等级，且用户类别包含资源类别 → 可读
    """
    return user_label.dominates(resource_label)

def mac_check_write(user_label: SecurityLabel, resource_label: SecurityLabel) -> bool:
    """
    *-属性规则（上写）：
    用户等级 <= 资源等级，且用户类别等于资源类别 → 可写
    防止高等级信息泄露到低等级资源
    """
    return (user_label.level <= resource_label.level and 
            user_label.categories == resource_label.categories)
```

#### 3.1.5 双模型切换实现

```python
# auth_gateway.py 全局配置
ACCESS_CONTROL_MODE = os.getenv("CLAWGUARD_MODE", "rbac")  # rbac | mac | hybrid

def check(user_id: str, path: str = "", tool: str = "", database: str = "") -> bool:
    """统一入口，根据模式选择校验逻辑"""
    
    if ACCESS_CONTROL_MODE == "rbac":
        return _check_rbac(user_id, path, tool, database)
    
    elif ACCESS_CONTROL_MODE == "mac":
        return _check_mac(user_id, path, tool, database)
    
    elif ACCESS_CONTROL_MODE == "hybrid":
        # 双重校验：必须同时通过 RBAC 和 MAC
        return (_check_rbac(user_id, path, tool, database) and 
                _check_mac(user_id, path, tool, database))
    
    return False  # 未知模式，默认拒绝
```

#### 3.1.6 创新点提炼

> **动态双模型切换机制**：传统系统通常只采用 RBAC 或 MAC 其中一种模型。本系统创新性地将两种模型融合，支持按场景动态切换。在普通业务场景使用灵活的 RBAC，在高安全场景切换为强制的 MAC，在核心涉密场景启用双重校验的 Hybrid 模式。这种设计兼顾了灵活性与安全性，填补了现有 LLM 代理访问控制领域的空白。

#### 3.2.3 持久化策略

| 方案 | 优点 | 缺点 | 建议 |
|------|------|------|------|
| 保留文本文件 | 简单直观，便于人工查看 | 并发编辑易冲突，无事务 | 开发/演示环境 |
| JSON 文件 | 结构化，易解析 | 仍有并发问题 | 小型项目 |
| SQLite 数据库 | 支持事务，并发安全 | 需要数据库连接 | **生产环境推荐** |
| 内存 + 定时持久化 | 性能最高 | 可能丢数据 | 高并发场景 |

**建议实现**：开发环境保留文本文件，生产环境自动迁移到 SQLite。

```python
class RuleStore:
    def __init__(self, backend: str = "auto"):
        """
        backend: "text" | "sqlite" | "auto"
        auto: 优先使用 sqlite，不存在则回退到 text
        """
        self.backend = self._init_backend(backend)
        self.reload()
    
    def add_user(self, user_id: str, level: int, specials: list[str]) -> bool:
        """统一接口，底层自动选择存储方式"""
        return self.backend.add_user(user_id, level, specials)
```

### 3.3 改进三：树状权限粒度

#### 3.3.1 设计思路

将扁平的资源规则升级为**树状层级结构**，支持目录继承和局部覆盖，实现精细化到文件级别的权限控制。

#### 3.3.2 树状规则格式

```
# resources_tree.txt — 树状资源规则
# 格式: 路径 | 等级 | 继承模式 | 类别(可选)

# 根级规则（默认继承）
C:\Users                | 2 | inherit | 用户目录
C:\Users\Public         | 1 | inherit | 公开目录
C:\Users\Public\*       | 1 | inherit | 公开子目录

# 局部覆盖（子目录覆盖父级）
C:\Users\admin          | 3 | override | 管理员目录
C:\Users\admin\secrets  | 4 | override | 机密子目录
C:\Users\admin\temp     | 2 | override | 临时目录降级

# 工具规则（独立命名空间）
tool:*                  | 2 | flat     | 默认工具权限
tool:write_file        | 3 | flat     | 写文件工具
tool:execute_bash      | 4 | flat     | 执行命令工具
```

#### 3.3.3 匹配算法

```python
def _resource_required_level_tree(path: str, tool: str = "", database: str = "") -> int:
    """
    树状资源匹配：从叶子节点向上回溯，找到最近的一条规则
    
    优先级：
    1. 精确匹配 > 前缀匹配 > 通配匹配
    2. 路径越深（越具体）优先级越高
    3. override 模式覆盖 inherit 模式
    """
    candidates = [p for p in (path, tool, database) if p]
    
    best_level = DEFAULT_RESOURCE_LEVEL
    best_depth = 0
    best_is_override = False
    
    for pattern, level, inherit_mode, categories in _store.tree_resources:
        for value in candidates:
            if not _match_pattern(pattern, value):
                continue
            
            # 计算匹配深度（路径层级数）
            current_depth = pattern.count("\\") + pattern.count("/")
            
            # 优先级判定
            if inherit_mode == "override":
                # override 总是优先于同深度的 inherit
                if current_depth > best_depth or (current_depth == best_depth and not best_is_override):
                    best_level = level
                    best_depth = current_depth
                    best_is_override = True
            else:  # inherit
                # inherit 只在比当前更深时才覆盖
                if current_depth > best_depth:
                    best_level = level
                    best_depth = current_depth
                    best_is_override = False
    
    return best_level
```

#### 3.3.4 可视化示例

```
C:\Users
├── Public                    [level=1, inherit]
│   ├── Documents             [level=1, inherit]
│   └── Downloads             [level=1, inherit]
│
├── admin                     [level=3, override]  ← 覆盖父级 C:\Users 的 level=2
│   ├── secrets               [level=4, override]  ← 覆盖父级 admin 的 level=3
│   │   └── nuclear_codes.txt [level=4, inherit]   ← 继承 secrets 的 level=4
│   └── temp                  [level=2, override]  ← 覆盖父级 admin 的 level=3
│
└── guest                     [level=1, inherit]
```
